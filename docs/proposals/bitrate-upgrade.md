# Предложение: аудит битрейта и замена треков через YouTube Music

Статус: **предложение, не реализовано**. Целевая версия — 1.2 (или 2.0 при
переезде в отдельный репозиторий).

## 1. Проблема

Яндекс Музыка перестала отдавать MP3 320 kbps: API возвращает только
`mp3 192` (иногда дополнительно `aac 128`). Проверка на реальном плейлисте из
1292 треков (выборка 50 треков) дала:

```text
49 × (('mp3', 192),)
 1 × (('aac', 128), ('mp3', 192))
```

То есть текущий `choose_best_download_info()` продолжает работать, но выбирать
ему больше нечего — новые треки сохраняются в 192 kbps.

Нужна отдельная команда, которая:

1. проходит по локальному архиву;
2. находит файлы с битрейтом ниже целевого;
3. ищет соответствующий трек в YouTube Music через `ytmusicapi`;
4. скачивает лучший доступный вариант;
5. безопасно заменяет файл в архиве, сохраняя резервную копию и отчёт.

## 2. Важное ограничение: `ytmusicapi` не умеет скачивать аудио

`ytmusicapi` — это обёртка над YouTube Music API для поиска, метаданных,
плейлистов и библиотеки. В списке возможностей нет получения аудиопотока или
скачивания файла. Поэтому архитектура будет такой:

```text
ytmusicapi  →  поиск трека, videoId, метаданные, длительность
yt-dlp      →  получение лучшего аудиопотока по videoId
ffmpeg      →  декодирование/кодирование в MP3 (если нужен MP3)
mutagen     →  проверка и запись ID3-тегов
```

`yt-dlp` и `ffmpeg` — внешние зависимости. Их наличие проверяется на старте
команды; без них `upgrade` завершается с понятной ошибкой, а `audit` работает.

### Битрейт — это не качество

YouTube Music отдаёт lossy-аудио (AAC/Opus, обычно 128–256 kbps). Перекодировка
в MP3 320 CBR **не добавляет качества** и может звучать хуже исходника. Поэтому
нельзя просто «догнать 320». Предлагается двухуровневая политика:

* **`--target-bitrate 320`** — верхняя граница, а не гарантия. Если источник
  lossy и его битрейт ниже 320, инструмент всё равно может заменить файл, но
  помечает результат как `transcoded` и пишет исходный кодек/битрейт в отчёт.
* **`--lossless-only`** — заменять только на lossless-источник (FLAC/WAV).
  Для YouTube Music это редкость, но флаг полезен, если позже добавится другой
  источник.
* **`--report-only`** (по умолчанию) — только найти кандидатов и показать
  отчёт. Замена выполняется только с `--apply`.

Это защищает от главной ошибки: массовой перекодировки 192 → 320, которая
увеличивает файлы, но не качество.

## 3. Архитектура

Новый пакет `ym_organizer` с подкомандами:

```text
python -m ym_organizer sync      # текущее поведение: докачать плейлист
python -m ym_organizer audit     # только отчёт по архиву
python -m ym_organizer upgrade   # поиск и (с --apply) замена
```

Модули:

| Модуль | Ответственность |
|---|---|
| `cli.py` | argparse/подкоманды, коды возврата |
| `config.py` | `.env`, пути, лимиты, флаги |
| `archive.py` | обход `TARGET_DIR`, чтение ID3, длительность, битрейт |
| `matching.py` | нормализация строк, скоринг кандидатов |
| `ytmusic.py` | обёртка над `YTMusic.search/get_song/get_album` |
| `downloader.py` | `yt-dlp` + `ffmpeg`, проверка результата |
| `replace.py` | backup, атомарная замена, откат |
| `manifest.py` | SQLite-манифест состояния и кэш поиска |
| `report.py` | CSV/JSON/Markdown-отчёт |

### Поток `upgrade`

```text
scan archive
  → filter bitrate < target
  → read tags + duration
  → search YT Music (cache)
  → score candidates
  → [report-only] write report and stop
  → [apply] download best candidate to temp
  → validate duration/codec/bitrate/playability
  → tag with original Yandex metadata
  → backup original
  → atomic replace
  → update manifest
```

### CLI (черновик)

```bash
# Отчёт: какие треки ниже 320 и что нашлось на YouTube Music
python -m ym_organizer upgrade --dir "C:\Users\north\Music\!All" --report report.csv

# Заменить первые 20 подходящих треков, с бэкапом
python -m ym_organizer upgrade --dir "C:\Users\north\Music\!All" --apply --limit 20

# Только один трек по локальному id
python -m ym_organizer upgrade --dir ... --apply --id 0042

# Строгий режим: только точные совпадения, без live/cover/remix
python -m ym_organizer upgrade --dir ... --apply --min-score 0.92 --no-live
```

Флаги:

| Флаг | Смысл |
|---|---|
| `--apply` | реально менять файлы; без него — отчёт |
| `--limit N` | максимум замен за запуск |
| `--min-score 0.85` | порог совпадения |
| `--duration-tolerance 5` | допустимая разница длительности, сек |
| `--backup-dir` | куда складывать оригиналы (по умолчанию `.backup/YYYYMMDD/`) |
| `--format mp3` | целевой формат; `keep` — не перекодировать |
| `--audio-quality 0` | качество `yt-dlp`/ffmpeg |
| `--workers 1` | параллелизм; по умолчанию 1, чтобы не злить API |
| `--resume` | продолжить по манифесту |
| `--report report.csv` | отчёт |

## 4. Сопоставление треков

Метаданные локального файла — основной источник, имя файла — резервный:

* `TPE1` (artist), `TIT2` (title), `TALB` (album), `TDRC` (year),
  `TLEN`/`mutagen` duration.
* Нормализация: Unicode NFKC, casefold, удаление пунктуации, схлопывание
  пробелов, унификация `feat.`/`ft.`, `remaster`, `deluxe`, `explicit`.
* Поиск: `YTMusic.search(f"{artist} {title}", filter="songs")`, при пустом
  результате — `filter="videos"`.
* Скоринг:
  * artist similarity — 0.40;
  * title similarity — 0.40;
  * duration closeness — 0.15;
  * album/year bonus — 0.05.
* Жёсткие отсечки:
  * `duration_delta <= max(5s, 2%)`;
  * artist и title каждый >= 0.80;
  * если разница между первым и вторым кандидатом < 0.05 — `ambiguous`,
    в отчёт, без автоматической замены;
  * исключать `live`, `cover`, `karaoke`, `instrumental`, `remix`, если этих
    слов нет в исходном названии (флаг `--no-live` и т.п.).
* Для `difflib.SequenceMatcher` достаточно stdlib; `rapidfuzz` — опционально
  для скорости на больших архивах.

## 5. Безопасность и идемпотентность

1. **По умолчанию ничего не менять.** `upgrade` без `--apply` — только отчёт.
2. **Бэкап перед заменой**: `TARGET_DIR/.backup/2026-10-19/0001. ...mp3`.
3. **Атомарная замена**: скачать в `TARGET_DIR/.tmp/`, проверить, затем
   `os.replace()`. Оригинал не трогается до успешной проверки.
4. **Проверка результата**:
   * файл читается `mutagen`;
   * длительность отличается не больше чем на допуск;
   * битрейт/кодек записаны в манифест;
   * при `--format mp3` — валидный MP3.
5. **Манифест SQLite** (`.ym-organizer.sqlite3`):
   ```sql
   tracks(path PRIMARY KEY, yandex_id, artist, title, album, duration_ms,
          old_bitrate, old_codec, status, candidate_video_id, candidate_title,
          candidate_artist, candidate_duration, score, new_bitrate, new_codec,
          source, backup_path, updated_at, error)
   ```
   Статусы: `new`, `matched`, `ambiguous`, `downloaded`, `replaced`,
   `rejected`, `no_match`, `failed`.
6. **Идемпотентность**: повторный запуск пропускает `replaced` и `rejected`;
   `failed` можно повторить с `--retry-failed`.
7. **Rate limiting**: задержка между запросами, retry с exponential backoff,
   `--workers 1` по умолчанию.
8. **Логи**: `logs/upgrade-YYYYMMDD-HHMMSS.log`, отчёт CSV/JSON.

## 6. Тестирование

* Unit-тесты matching на фикстурах ответов `ytmusicapi` (без сети).
* Unit-тесты `archive`/`replace` на временном каталоге с fake MP3.
* Integration-тест с fake `YTMusic` и fake downloader: полный проход
  `scan → match → replace`, проверка бэкапа и манифеста.
* `--report-only` на реальном архиве — безопасный smoke-тест.
* Сетевые тесты — отдельный маркер `@pytest.mark.live`, по умолчанию skip.

## 7. Зависимости

```toml
[project]
dependencies = [
  "yandex-music>=3.2.2,<4",
  "ytmusicapi>=1.12,<2",
  "yt-dlp>=2026.8.19",   # обновлять регулярно, API YouTube меняется
  "mutagen>=1.47",
  "python-dotenv>=1.0",
]
```

`ffmpeg` — системная зависимость. `yt-dlp` лучше держать в lockfile и обновлять
чаще, чем остальные пакеты: YouTube регулярно ломает извлечение.

## 8. Стратегия репозитория

### Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Оставить текущий форк**, добавить `ytmusicapi`/`yt-dlp` | ничего не мигрируем; история и релизы на месте | 69k строк vendored-библиотеки; каждый sync — merge на 65+ коммитов; версии приложения и библиотеки смешаны; конфликты тегов |
| **B. Новый standalone-репозиторий** `ym-organizer`, зависимости из PyPI | чистый app-репозиторий; свои релизы; обновления зависимостей через lockfile/Renovate; нет merge-боли | одноразовая миграция; нужно перенести код и историю |
| **C. «Форк двух репозиториев»** (vendored `yandex-music` + `ytmusicapi`) | формально «всё своё» | худший вариант: два vendored-дерева, два upstream-мержа, никакой выгоды; Git всё равно не умеет «двух родителей» |
| **D. Монорепо с submodules** | видно версии | submodules усложняют CI, релизы и обновления; для двух библиотек не оправдано |

### Рекомендация

**Вариант B: новый standalone-репозиторий приложения, без форка
`ytmusicapi`.** Это то, как обычно делают в индустрии:

* форкают только то, что действительно патчат;
* библиотеки подключают как зависимости с lockfile;
* если нужен патч — используют fork + git-источник в пакетном менеджере
  (`[tool.uv.sources]`, `pip install git+https://...`), а не vendoring;
* приложение и библиотека имеют независимые версии и релизный цикл;
* обновления зависимостей автоматизируются (Renovate/Dependabot).

Текущий форк при этом не «пропадает»: он остаётся историей версии 1.1 и может
использоваться, если понадобится патчить саму `yandex-music-api`. Но новую
функциональность лучше развивать в отдельном репозитории.

### План миграции

1. Зафиксировать текущее состояние: релиз `organizer-v1.1.0` в форке.
2. Создать `ym-organizer` (или `ym-archive-organizer`).
3. Перенести CLI в пакет `ym_organizer/` (не один скрипт в корне).
4. Добавить `pyproject.toml` с зависимостями, `uv.lock`, CI (pytest + ruff).
5. Реализовать `audit` и `upgrade` (сначала report-only).
6. Выпустить 2.0.0 — новая архитектура, новый репозиторий.
7. В старом форке добавить в README ссылку на новый репозиторий; при желании
   архивировать.

### Если решено остаться в текущем форке

Тогда минимум:

* не фетчить upstream-теги (`git fetch upstream main` без `--tags`);
* релизы тегировать `organizer-vX.Y.Z`;
* добавить `ytmusicapi`/`yt-dlp` в отдельную optional-группу зависимостей;
* не добавлять второй vendored-репозиторий.

## 9. Риски и ограничения

* YouTube может требовать cookies/PO token для части треков; предусмотреть
  `--cookies` и `--cookies-from-browser` (проброс в `yt-dlp`).
* Результаты поиска зависят от региона и языка; `ytmusicapi` поддерживает
  параметры `location`/`language`, их нужно зафиксировать в конфиге.
* `yt-dlp` ломается при изменениях YouTube; версию нужно обновлять чаще
  остальных зависимостей и иметь возможность откатиться.
* Ошибочное сопоставление может заменить трек другой версией. Поэтому
  `ambiguous`-кандидаты не заменяются автоматически, а попадают в отчёт.
* Lossy-источник + перекодировка в MP3 320 не гарантируют улучшения качества;
  политика `--report-only` по умолчанию и статус `transcoded` в манифесте
  обязательны.
* Массовая замена 1600+ файлов — долгая операция; нужны `--limit`, `--resume`
  и понятный прогресс.

## 10. Открытые вопросы

1. Считаем ли замену из YouTube Music улучшением, если источник lossy
   (AAC/Opus), а результат — MP3 320? Или заменять только при lossless?
2. Нужна ли автоматическая замена или только отчёт + ручное подтверждение?
3. Хранить ли обе версии (192 и новую) или заменять с бэкапом?
4. Обновлять ID3-теги из YouTube Music или сохранять исходные яндексовские?
5. Есть ли YouTube Music Premium? Это влияет на доступные потоки и качество.
6. Насколько строго отсекать live/cover/remix? Предлагаемый порог — 0.85,
   но для редких треков его придётся снижать вручную.

## 11. Правовое замечание

Скачивание аудио с YouTube Music может нарушать условия использования сервиса.
Инструмент предназначен для личного архива; ответственность за использование
лежит на пользователе. `yt-dlp` и `ytmusicapi` — сторонние проекты, не
аффилированные с YouTube/Google.
